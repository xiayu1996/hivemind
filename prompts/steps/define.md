# 步骤：定义产品

把需求写成 `PRODUCT.md` 与 `acceptance.yaml`。人会先批准这两份，之后的一切都照着它们做、照着它们验，
所以契约没写进去的东西就不会被做出来，写进去的每一条都会在真实浏览器里被逐条验收。

## 先看现场

目标仓库已经有产品时（有代码、或已有 `.hivemind/` 文件），先弄清它现在能做什么：
已有的验收项与 id 保持不变，只在需求要求改变它时才改；新功能加新的验收项，编号接着往后排。

## PRODUCT.md

写给批准它的人，中文业务语言：
1. 为谁、解决什么问题——一段话。
2. 核心使用流程：人从打开产品到完成目标，依次做什么、看到什么。
3. 明确不做的事，以及为什么这一版不做。

## acceptance.yaml

- **完整覆盖需求**。每条核心流程都要有验收项；一个需求读下来人会期待的东西，契约里都要找得到，或者明确列在 `outOfScope`。
  宁可多几条小场景，也不要一条什么都说的大场景。
- **按用户怎么用来分验收项**，不按技术模块分：一个验收项是一段用户能独立完成、独立验收的事。
- 每条会改变存储的场景都配一条"重新打开还在"的场景（`mutates` / `persistedBy`）。
- 空态、错误态这些用户真会遇到的状态，是需求的一部分时就写成场景。

## 结果

`summary` 用两三句话告诉批准的人这一版会做成什么样；`decisions` 列出你替人做的范围取舍。
需求本身有两种合理解读、会做出完全不同的东西、又查不到依据时，才进 `questions`。
