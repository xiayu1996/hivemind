# 步骤：技术方案

替整个需求定一次技术方案：写 `ARCHITECTURE.md` 与 `project.yaml`。这是仓库级、影响之后每一项构建的决定，
所以在这里定，而不是让第一个写代码的会话顺手决定。人会批准它。

## 先看现场

仓库已经有代码时，默认沿用它的技术栈、目录习惯与检查方式；只有沿用会让需求做不成、或明显更贵时才提出改动，
并把理由写进 `decisions`。空仓库就从需求出发选：选社区主流、文档充分、本机能跑的，不选新奇的。

## ARCHITECTURE.md

1. 技术栈：语言、运行时、框架、存储，以及认真考虑过又否掉的备选与理由。
2. 模块划分：目录结构、每个模块负责什么、谁依赖谁。
3. 数据与持久化：存什么、存在哪、怎么迁移。会改变存储的场景都依赖这一节。
4. 产品入口：人怎么打开这个产品。`app.start` 必须启动的就是它——不另写演示入口。
5. 测试策略：单测测什么、怎么起真实服务做集成测试；新代码按什么约定写测试。
6. 约定：命名、错误处理、日志，构建者写每一行代码时要遵守的那几条。

## project.yaml

- `checks` 至少有类型检查（或编译）与测试；它们定义了什么叫"绿"，构建者改不了它们。
- 有 web 场景就必须有 `app`：`start` 监听 `127.0.0.1`、端口取 `{port}` 或 `PORT`；`ready` 是一个起好之后一定应答的路径。
- 场景需要造数时提供 `app.seed`，接受场景里写的 seed 名。
- 所有命令都要能在一个全新的工作区里、只跑过 `setup` 之后成功。

地基（工程骨架、检查全绿、产品能启动）会作为计划的第一项被构建出来，这里只需把它描述清楚。
