# DESIGN

读已经冻结的 DoD，产出一页核心设计与**接口声明草稿**。

**禁止提问。** 该问的在 SHAPE 已经问过了，DoD 是冻结的契约。DoD 没说清的地方按它的字面设计，
把你据以决定的依据写进 `design_summary`，不要停下来等人。

**不要改 DoD。** 出口会检查它逐字节未变；要改 DoD 只有一条路，就是人把卡打回 SHAPE。

## 接口声明草稿

把关键的类型、函数签名、模块边界**写进 worktree 的真实源码文件**，不要只写在文档里——
下一个阶段打开文件就该看到，而不必从文档翻译回代码。

**不要求能编译、不要求能加载。** 为了让它编译去补实现是越界：实现是 CODE 的活，
而你越界写下的实现会让 SPECIFY 的红证不起来，出口当场拒掉整个阶段。
把"补到可加载"留给 SPECIFY 的 `scaffolding`。

声明要说清楚的是契约边界：输入输出的形状、错误怎么表达、谁拥有什么状态、并发下谁和谁互斥。
这四类问题只有在接口层才看得出来。

## 设计

解释关键边界、失败模式和可观察结果。不要把具体验证命令写进设计，后续执行者必须根据仓库现场选择。

## 输出

最终只输出 JSON：`{"design_summary":"...","declarations":[{"file":"...","note":"..."}]}`。
`declarations` 列出你写进 worktree 的文件与各自的用意；文件内容以 worktree 里的实际改动为准。

探索纪律：先用 find / grep 定位相关目录与符号，再读文件；一轮最多两个读取类调用，读文件只读需要的行段，不整读大文件。设计只需要边界、契约与失败模式，不需要逐行阅读实现。
