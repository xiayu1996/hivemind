编号节点问题证据状态

F3CODE 出口completion judge 是 LLM，只看最后 20 条工具结果，曾误判"没有 commit"、要求浏览器证据。它的否决直接走 retry_limit_exceeded。P17 / P18；E1ACTION 三条 "Evidence is insufficient"部分修，未提交
F4VERIFY盲审要自己起服务、选端口、截图到指定目录，全靠 prompt 约束。出现过起不了服务、端口互撞、截图落进 worktree 触发 tree-pin 崩溃、用 route 伪造接口。P14 / P15 / P22 / P23 / P28逐个补丁，未提交
F5收敛判据环境故障（服务 404）被记成场景失败，failed 集合被污染后判 expanded 直接停。历史按上次人工动作截断，MERGE 退回的轮次曾让 worker 直接崩。21:15 第 2 轮 4 场景失败原因都是 "Route GET:/api/overview not found"；P26设计层
F6MERGE只读阶段，却是唯一执行 git diff --check 的地方，且由 agent 自选。失败后曾映射回 MERGE 原地再停，CODE 拿不到原因。6 次 retry_limit_exceeded 同一原因；P24 / P29已修，未提交
F7合流复验盲审 runner 的 cwd 固定为 Story worktree，截图落错目录，校验器在 integration 目录找不到 → 全场景失败。P31 改会话名没有触及。scripts/run-story.ts:170；E2RESULTS 10 轮、E1ACTION 7 轮未修
F8合流复验每次合流都重跑一遍完整浏览器盲审，成本与首轮 VERIFY 相同。失败后回 CODE 但 worktree 不动，CODE 只能重新走整轮内环。cost_entries：VERIFY 与 CODE 花费相当设计层
F9交付Epic 内 Story 不开 MR，Epic MR 要等全部 Story 交付并集成。一个"小任务"没有任何人可见的交付物。story-delivery.ts:61；run-local-orchestrator.ts:511设计层
F10停点与供应商usage limit、超时、OAuth 401 与代码失败共用 retry_limit_exceeded；熔断探测方式是真派单，每次探测消耗一次尝试；usage limit 文案不带重置窗口时盲猜 30 分钟；多个 pi 进程共享一份 OAuth 凭据并发刷新。三张卡 phase.failed 约 45 条，供应商类约 31 条；provider.opened 只记录 1 次未修

4. 结构性观察

一轮内环里串着 5 个 fail-closed 的 LLM 判定：CODE agent、CODE completion judge、VERIFY agent、MERGE agent、MERGE completion judge；合流再加一个盲审 agent。每个节点的否决都被当成"代码有问题"计入预算。即使每个节点 90% 可靠，一轮全过的概率也只有 0.96 ≈ 53%，而任何一次供应商故障都会再吃掉一次预算。这比任何单个 bug 更能解释"小任务跑不完"。
