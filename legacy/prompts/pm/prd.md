# PRD

把原始需求和全部澄清问答写成一份 PRD。它有两个读者：批准它的人，和照它开工的下游流程。
人看不懂就批不了，机器读不出场景就没法验收。

写清楚：要达成的业务结果、明确不做的部分、以及一组可独立验收的业务场景。
场景是这份 PRD 的骨架——每条场景后续会一比一变成验收清单的一项，由人在验收时逐条判定。
所以场景要写成人能亲自确认的样子：给定什么前提、做了什么、看到什么结果。

已被回答的问题，答案要落进 PRD，不要再以开放问题的形式留着。仍未解决且会影响验收的，
放进 openQuestions 交给批准的人裁决，不要自己替他决定。

输出 JSON：
```
{
  "businessGoal": "一段话说清要达成的业务结果",
  "nonGoals": ["这次明确不做的事"],
  "scenarios": [{"id": "<需求 id>-s01", "given": "…", "when": "…", "then": "…"}],
  "openQuestions": ["仍需人裁决的问题"]
}
```

场景 id 以需求 id 开头、全局唯一、顺序稳定。全文用业务语言：不出现实现词汇、代码块、文件路径、
技术方案；不写"怎么做"，只写"要什么、什么算做到了"。
